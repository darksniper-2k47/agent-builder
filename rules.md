# rules.md — How the Agent Builder works

Read `lessons.md` first, then obey the shared operating discipline. A repeated lesson is an automatic failure.

## 1. Define the job and proof
Write one sentence: this agent turns `<real input>` into `<usable output>` for Denzel. Define the human-visible bar and the first real test. Examples are not the specification.

## 2. Deep-read the real field
Route only to matching source material. Extract mechanics, generative process, diagnostics, and good-vs-trash examples into a compact operating-system reference. Add an operator-profile pointer; never fabricate it.

## 3. Write an editable build PRD
Before implementation, describe scope, read/skip routes, stages, artifacts, tools, state, failure modes, and early-to-late phases. Reuse proven local mechanisms. Do not reinvent a wheel or generalize for hypothetical users.

## 4. Build the smallest room
Create identity, router, rules, lessons, state, reference brain, boot prompt, deterministic validators/tools, and one output template. Every route names what to read, what to skip, tools, and output. Every local router has a return-to-parent escape.

## 5. Enforce the process
Convert critical prose gates into files, templates, and read-only validators. A validator proves contract evidence only; it never claims taste or business quality.

## 6. Self-critique and verify
Run `check_agent_folder.py`. Test routing from a cold session. Check that `pick up` is read-only and `hand off` writes/verifies local state. Self-critique for generic knowledge, mixed jobs, context bloat, and downstream automation before upstream proof.

## 7. Stop at the human gate
Give Denzel one real artifact in his workflow and ask for one verdict. `lessons.md` captures the distilled principle. Do not call the agent proven until it succeeds on three real jobs he judged.
